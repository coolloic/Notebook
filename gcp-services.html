GCP services & Infrastructure as Code

Google Cloud gives you the same building blocks as any hyperscaler — compute, storage, databases, data pipelines, networking, AI — but its real strengths are data analytics (BigQuery), containers (GKE, Cloud Run) and ML (Vertex AI). And however you build, you should define it in code, not clicks. This guide tours the core GCP services, then introduces Infrastructure as Code to provision them repeatably.

Two halves. First, a field guide to the services worth knowing and what each solves. Second, how to create them — not by clicking in the console (which drifts and can't be reviewed) but declaratively with IaC, mainly Terraform. The companion AWS field guide and Cloud Native tutorials pair well with this.

Foundations  The GCP resource hierarchy

Before services, learn how GCP organises them — it drives billing, IAM and blast radius. Everything lives in a tree:

LevelWhat it is
OrganizationRoot node tied to your domain — company-wide policies live here.
FolderOptional grouping (by department, team, or environment).
ProjectThe core unit — every resource belongs to exactly one project; it's the boundary for billing, quota, IAM & APIs.
ResourcesThe actual services (a VM, a bucket, a database) inside a project.

Two more concepts you'll meet constantly:

Where it runs

Regions & zones

A region (e.g. us-central1) is a geographic area; a zone (us-central1-a) is one datacenter within it. Spread across zones for HA.

Who can do what

IAM

Grant roles (bundles of permissions) to principals (users, groups, service accounts) on a resource. Service accounts are the identity your workloads use.

Rule of thumb: one project per app per environment (e.g. shop-prod, shop-staging). It cleanly isolates billing, quotas and permissions — and maps neatly onto separate IaC state.

Second half  What is Infrastructure as Code?

Infrastructure as Code (IaC) means defining your cloud resources — VMs, buckets, databases, networks, IAM — in text files under version control, and letting a tool create and update them to match. You describe the desired state; the tool figures out the API calls.

The problem it solves

Click-ops

Drift & snowflakes

Consoles create one-off "snowflake" environments no one can reproduce. Staging never quite matches prod.

No history

No review, no audit

A click leaves no diff, no PR, no reviewer. Who opened that firewall port, and when?

Manual

Slow & error-prone

Rebuilding an environment by hand takes days and misses steps. Disaster recovery is a prayer.

Declarative vs imperative. IaC is usually declarative: you state the end result (“a bucket named X in region Y”) and the tool reconciles reality to it — creating, updating, or deleting as needed. An imperative script (a pile of gcloud commands) lists steps and can't tell what already exists. Declarative is idempotent: run it twice, get the same result.
What you get: reproducible environments (spin up an identical stack in minutes) · code review & audit for every infra change · easy rollback (revert the commit) · self-documenting infrastructure · consistent dev/staging/prod from the same modules.

Options  IaC tools for GCP

ToolWhat it isUse when…
Terraform / OpenTofuDeclarative, cloud-agnostic (HCL). The de-facto standard; OpenTofu is the open-source fork.Almost always — largest ecosystem, multi-cloud, huge module registry.
Config ConnectorManage GCP resources as Kubernetes objects (KRM).You're all-in on GKE and want GitOps via Kubernetes tooling.
PulumiIaC in real languages (TypeScript, Python, Go).Your team prefers a general-purpose language and loops/abstractions over HCL.
gcloud CLI / scriptsImperative commands.Quick experiments & exploration — not durable infrastructure (no state, drifts).
Deployment ManagerGCP's native (legacy) IaC.Rarely for new work — Google steers toward Terraform now.
The gcloud trap: shell scripts of gcloud commands feel like IaC but aren't — there's no state file, so the tool can't detect drift, plan a diff, or safely delete what you removed. Use gcloud to explore; use Terraform to own infrastructure.

Hands-on  Terraform on GCP — a walkthrough

Terraform's loop is write → plan → apply, with a state file recording what it manages so it can compute the diff between your code and reality.

1 · Configure the provider

# main.tf — tell Terraform to manage GCP
terraform {
  required_providers {
    google = { source = "hashicorp/google", version = "~> 5.0" }
  }
  # Remote, locked state in a GCS bucket (see best practices)
  backend "gcs" { bucket = "my-tfstate", prefix = "shop/prod" }
}

provider "google" {
  project = "shop-prod"
  region  = "us-central1"
}

2 · Declare resources

# A bucket and a Cloud Run service — the desired state
resource "google_storage_bucket" "assets" {
  name          = "shop-prod-assets"
  location      = "US"
  force_destroy = false
}

resource "google_cloud_run_v2_service" "api" {
  name     = "shop-api"
  location = "us-central1"
  template {
    containers { image = "us-docker.pkg.dev/shop-prod/app/api:1.4.0" }
  }
}

3 · Plan, then apply

terraform init      # download providers, wire up the backend
terraform plan      # preview: what will be created/changed/destroyed
terraform apply     # make it so; records outcome in state

# Example plan summary:
Plan: 2 to add, 0 to change, 0 to destroy.
Always read the plan. Before apply, scan for destroy lines — Terraform will happily replace a database if a change forces it. In CI, run plan on the PR and require human approval before apply.

4 · Reuse with variables & modules

# Same module, different envs — no copy-paste
module "service" {
  source = "./modules/cloud-run-api"
  env    = var.env        # "staging" or "prod"
  image  = var.image
}

Do it right  IaC best practices

PracticeWhy
Remote state + lockingStore state in a GCS backend, not on a laptop. Locking stops two people applying at once and corrupting it.
Plan in CI, apply on approvalEvery change is a reviewed PR with a plan attached — no surprise applys.
No secrets in codeReference Secret Manager; never hard-code keys. State can contain secrets — encrypt & lock it down.
Modules for reuseOne tested module per pattern; compose environments from it instead of copy-paste.
Separate state per environmentIsolate prod from staging so a mistake can't cross the boundary.
Least-privilege service accountThe CI identity that runs Terraform gets only the roles it needs. See security.
Detect driftRun plan on a schedule; a non-empty diff means someone click-opped — reconcile it.
The mindset: the console is read-only. If a change isn't in a merged commit, it didn't happen — and it'll be reverted on the next apply. That single discipline is what makes infrastructure reproducible, reviewable and recoverable.
