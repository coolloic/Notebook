Loop engineering — getting started with loops

A loop is an agent repeating cycles of work until a stop condition is met. It's a shift from one-shot prompting toward designing automated workflows that iterate on their own — gathering context, acting, verifying, and going again until they're done.

trigger→ gather → act → verify↺ repeat until…→ stop
Why loops. Single turns need you between every step. Loops move you out of the inner cycle — handing off the triggering, the verification, and the stopping — so the agent iterates on complex or recurring work without you as the bottleneck.

Framing  Anatomy of a loop

Every loop is defined by three choices. Nail these and you've designed the loop:

▶️ Trigger

What starts a cycle — a manual prompt, a schedule, an event, or a goal being defined.

🛑 Stop criteria

What ends it — a user action, a goal achieved, a turn limit, or external completion.

🧩 Primitive

Which Claude Code capability powers it — skills, auto mode, or dynamic workflows.

Design tip. Prefer deterministic stop criteria — "tests pass," "score ≥ 0.9," "no new items" — over subjective judgments. They're what make a loop safe to run unattended.

The taxonomy  The four loop types

Loops fall into four kinds, along a ladder of increasing autonomy:

① Turn-based manual, one cycle at a time

Trigger A manual prompt. Stops when you take the next action. Use for exploratory or high-touch work where you steer every turn.

② Goal-based /goal — iterate to a target

Trigger You define success criteria. Stops when an evaluator confirms the goal is met (with a turn cap as a backstop). Use for "make the tests pass," "get the score above X."

③ Time-based /loop · /schedule — recurring

Trigger A schedule / interval. Stops per run (or on your cancel). Use for recurring work — "summarize the #eng Slack every morning," monitoring an external system that changes over time.

④ Proactive fully autonomous routines

Trigger Schedule/event, combined with goals + workflows + auto mode. Stops on goal completion or external completion. Use for well-defined work: bug triage, issue handling, migrations, dependency upgrades.

The toolbox  The primitives that power loops

📋 Skills

Verification standards encoded as SKILL.md files, so the agent can self-check its work against your criteria.

⚙️ Dynamic workflows

Orchestrate multiple agents in parallel to decompose and cover a task (a research-preview capability).

⚡ Auto mode

Execute steps without pausing for permission — removes approval delays inside the loop.

🧑‍🔧 Subagents

Specialized agents for focused sub-tasks (e.g. an independent reviewer) within a larger loop.

loops as slash commands (illustrative)
# Time-based: recurring summary
/loop 24h   summarize yesterday's #eng Slack and post the highlights

# Goal-based: iterate until a deterministic criterion is met
/goal       make the failing tests in tests/ pass   # evaluator checks; turn cap as backstop

# Proactive routine: schedule + goal + workflow + auto mode
/schedule 1h  triage new bug reports, fix, open a PR, and request review

# Keep an eye on cost & progress
/usage       ·   /workflows   ·   /goal   (metrics & dashboards)

In practice  A worked example — proactive bug triage

A single proactive loop can own a recurring chore end to end by combining the primitives:

⏱ /schedule 1h→ check for new bug reports→ ⚙️ workflow: triage · fix · review (parallel)→ 📋 goal + skills verify→ open PR

Here /schedule checks for new reports hourly (trigger), /goal plus a verification skill defines "done" (stop), dynamic workflows triage, fix and review in parallel, and auto mode removes approval delays. You review the PRs — not every step.

How to begin  Getting started

#Step
1Identify a task where you are the bottleneck.
2Decide what you could hand off — the verification, the stop condition, the triggering.
3Pick the loop type that matches (turn / goal / time / proactive).
4Run it and observe where it stalls or over-reaches.
5Iterate on the design — tighten criteria, adjust cadence, add a review subagent.
Start small. Not every task needs a complex loop — begin with the simplest type that removes you from the cycle, and climb toward proactive only as trust and criteria firm up.

Guardrails  Best practices & limits

Keep loops trustworthy

Do Keep the codebase clean (the agent follows existing patterns), encode verification standards in skills, keep docs accessible, and deploy a secondary agent for independent review.

Manage cost & runaway

Do Match primitives and models to task complexity; use deterministic scripts for routine work instead of reasoning; align schedule intervals with how often things actually change; pilot dynamic workflows before scaling; and monitor with /usage, /goal metrics and the /workflows dashboard.

Watch Token cost scales with agent complexity and frequency; turn caps prevent runaway iterations but need calibration; subjective stop criteria are unreliable — prefer measurable ones.

The mindset shift. Loop engineering is less about writing a clever prompt and more about designing a system: what triggers it, how it verifies itself, and when it stops. Get those right and the agent does the loop; you do the review.
