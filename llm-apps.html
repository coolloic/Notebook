Building LLM Applications

A hands-on tour of the tools you use to turn a raw language model into a real application — organized around the three problems you hit as your app grows up.

Problem 1

Too much glue code

Prompts, parsing, tools, retrieval — LangChain gives you reusable building blocks.

Problem 2

Logic isn't a straight line

Loops, branches, multiple agents — LangGraph gives you stateful orchestration.

Problem 3

It's a black box

Can't see or measure it — LangSmith gives you tracing & evaluation.

How to use this page. Read top to bottom — each section builds on the last. Code blocks with tabs let you compare options; hit Copy to grab any snippet. There's a short quiz at the end to check what stuck.

Problem 1  LangChain — building blocks

Calling a model directly is easy for one prompt. A real feature needs prompt templating, output parsing, tool-calling, memory, and — to ground answers in your own data — document loading, chunking, embedding, and retrieval. LangChain provides standard, composable pieces so you write that glue once and swap providers with a one-line change.

input→ retrieve→ prompt→ model→ parse

The LCEL pipe (|) composes these into a chain with streaming, batching, and async for free. Here's the same minimal chain across two providers:

chain.py
# pip install langchain-anthropic
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate

model  = ChatAnthropic(model="claude-opus-4-8")
prompt = ChatPromptTemplate.from_template("Summarize in one sentence: {text}")
chain  = prompt | model

print(chain.invoke({"text": "..."}).content)
# pip install langchain-openai
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

model  = ChatOpenAI(model="gpt-4o")
prompt = ChatPromptTemplate.from_template("Summarize in one sentence: {text}")
chain  = prompt | model

print(chain.invoke({"text": "..."}).content)

Notice only the import and class name changed — the chain is identical. That provider-agnostic interface is LangChain's core value.

2 · RAG — grounding answers in your data

Retrieval-Augmented Generation feeds the model only the chunks of your documents relevant to a question, so it answers from your data instead of guessing. The pipeline is a straight line — no loops — which makes it a perfect LangChain chain.

documents→ split→ embed→ store→ retrieve→ answer
rag.py
# load → split → embed → store → retrieve → grounded answer
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

docs   = TextLoader("kb.txt").load()
chunks = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50).split_documents(docs)
store  = FAISS.from_documents(chunks, HuggingFaceEmbeddings(
             model_name="sentence-transformers/all-MiniLM-L6-v2"))
retriever = store.as_retriever(search_kwargs={"k": 4})

prompt = ChatPromptTemplate.from_template(
    "Answer using ONLY this context:\n{context}\n\nQuestion: {question}")
model  = ChatAnthropic(model="claude-opus-4-8", temperature=0)

chain = ({"context": retriever, "question": RunnablePassthrough()}
         | prompt | model | StrOutputParser())

print(chain.invoke("What is our refund policy?"))
Where do the chunks live? In a vector database. This example uses an in-memory FAISS index; section 5 covers the real storage options.

Problem 2  LangGraph — stateful orchestration

A chain is a one-way pipe. The moment your app must loop ("keep using tools until you can answer"), branch ("refund vs. escalate"), coordinate multiple agents, or pause for a human, you need a graph. LangGraph models your app as nodes (steps) connected by edges (control flow) that share a state object — and edges may form cycles.

START→ agent⇄ tools→ END

The agent ⇄ tools cycle is the reason→act→observe loop a chain can't express.

agent.py
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage

@tool
def calculator(expression: str) -> str:
    """Evaluate arithmetic, e.g. '15 * 0.2'."""
    return str(eval(expression, {"__builtins__": {}}))

model = ChatAnthropic(model="claude-opus-4-8").bind_tools([calculator])

class State(TypedDict):
    messages: Annotated[list, add_messages]

def call_model(state): return {"messages": [model.invoke(state["messages"])]}

g = StateGraph(State)
g.add_node("agent", call_model)
g.add_node("tools", ToolNode([calculator]))
g.add_edge(START, "agent")
g.add_conditional_edges("agent", tools_condition)  # branch: tool or done?
g.add_edge("tools", "agent")                        # loop back
graph = g.compile()

out = graph.invoke({"messages": [HumanMessage("What's 15% of 240?")]})
print(out["messages"][-1].content)
What does the graph buy you over a chain?

The loop lets the model call several tools in sequence, reacting to each result. The conditional edge decides at runtime whether to act or answer. Add a checkpointer and the run becomes durable, resumable, and human-in-the-loop-ready (pause before a tool, wait for approval, resume).

Problem 3  LangSmith — see & measure it

LLMs are non-deterministic. When an answer is wrong, was it bad retrieval, a weak prompt, or the model? LangSmith gives you a trace — a nested tree of every step with latency, tokens, and cost — plus evaluation to catch regressions before shipping. It auto-instruments LangChain & LangGraph with zero code change:

terminal
# the RAG chain and agent above are now fully traced
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="..."

What a trace looks like

Running the agent on "What's 15% of 240?" produces a run tree — the three LLM calls are the reason→act→observe loop made visible:

▸ LangGraph run · agent            3.1s · 1,240 tok · $0.021 ✅
   ├─ agent · LLM call #1          0.9s · 320 tok · calls calculator('240*0.15')
   ├─ tools · calculator          0.02s · returns '36'
   └─ agent · LLM call #2          0.8s · 360 tok · final answer ✅

Evaluation — did my change help?

eval.py
from langsmith import Client, evaluate

client = Client()
client.create_dataset("qa")  # add {question → reference answer} examples

def target(inputs):  # the system under test (your RAG chain)
    return {"answer": rag_chain.invoke(inputs["question"])}

def correct(outputs, reference_outputs):  # a grader
    return reference_outputs["answer"].lower() in outputs["answer"].lower()

evaluate(target, data="qa", evaluators=[correct], experiment_prefix="rag-v1")
# change a prompt → run "rag-v2" → compare scores side by side

5 · Vector databases — where chunks live

An embedding turns text into a vector positioned so similar meanings sit close together. A vector database stores those vectors + metadata and finds the nearest ones to a query — fast, over millions of items. That "semantic search" is the retrieval engine behind RAG.

DatabaseTypeBest for
ChromaOSS, embedded/serverPrototyping, local RAG
FAISSOSS library, in-processStatic, read-heavy, research
QdrantOSS server (Rust)Balanced prod, rich filters
PineconeManaged cloudHands-off production
pgvectorPostgres extensionAlready on Postgres

The storage flow never changes — only the client does. Compare storing the same chunks in two backends:

store_chunks.py
# pip install chromadb
import chromadb
from chromadb.utils import embedding_functions

client = chromadb.PersistentClient(path="./chroma_db")
ef = embedding_functions.SentenceTransformerEmbeddingFunction("all-MiniLM-L6-v2")
col = client.get_or_create_collection("policies", embedding_function=ef)

col.add(                       # store: Chroma embeds for you
    ids=[f"chunk-{i}" for i in range(len(chunks))],
    documents=chunks,
    metadatas=[{"source": "policy.txt"} for _ in chunks])

print(col.query(query_texts=["Can I get money back?"], n_results=2)["documents"])
# pip install qdrant-client sentence-transformers
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct
from sentence_transformers import SentenceTransformer

m = SentenceTransformer("all-MiniLM-L6-v2")
c = QdrantClient(":memory:")
c.recreate_collection("policies",
    vectors_config=VectorParams(size=384, distance=Distance.COSINE))

vecs = m.encode(chunks, normalize_embeddings=True)
c.upsert("policies", [                        # store: id + vector + payload
    PointStruct(id=i, vector=v.tolist(), payload={"text": chunks[i]})
    for i, v in enumerate(vecs)])

q = m.encode(["Can I get money back?"], normalize_embeddings=True)[0].tolist()
print([h.payload["text"] for h in c.search("policies", q, limit=2)])
Rule of thumb: start local with Chroma/FAISS to build the pipeline, then swap in a server (Qdrant/Pinecone/pgvector) when you need scale — the chunk → embed → upsert → query flow is identical.

6 · create-llm-app — scaffold it all

Everything above is wired together by create-llm-app, a CLI that generates a runnable project. You pick a provider, an app type (chat / RAG / agent), and whether to enable LangSmith tracing — it emits main.py, requirements.txt, .env.example (loaded via python-dotenv), and more.

terminal
# install
pip install -e .

# interactive — prompts for provider, app type, tracing
create-llm-app new my-assistant

# or non-interactive with flags
create-llm-app new my-rag --provider anthropic --type rag --no-tracing

cd my-rag
pip install -r requirements.txt
cp .env.example .env     # add your API key(s)
python main.py
pick provider→ pick app type→ tracing on/off→ runnable project

Under the hood it maps your choices to a provider registry and renders Jinja2 templates — the same chat / RAG / agent code you saw in sections 1–3.

7 · Agentic patterns & techniques

Once a single agent isn't enough, you compose multiple — and there's a small catalogue of proven shapes for doing so. This repo has a runnable scaffold for each, following Google Cloud's Choose a design pattern for your agentic AI system, built on the same LangChain / LangGraph / LangSmith stack from this tutorial.

The doc's key axis is who decides the route:

predetermined route — code decides — sequential · parallel · loop vs AI decides — model routes — coordinator · hierarchical · swarm

Design patterns (Google Cloud)

#PatternWhen to useStack
01Single-AgentModerate multi-step tasks, no delegationLangGraph (prebuilt ReAct)
02SequentialStructured, repeatable pipelinesLangChain (LCEL)
03ParallelIndependent sub-tasks; diverse perspectives at onceLangChain (RunnableParallel)
04LoopIterative refinement with an exit conditionLangGraph (cycle)
05Review & CritiqueHigh accuracy / compliance validationLangGraph (generator + critic)
06Iterative RefinementOutput hard to nail in one shot; quality gateLangGraph (self-score loop)
07CoordinatorAdaptive routing of varied inputsLangGraph (router)
08HierarchicalAmbiguous, open-ended problemsLangGraph (orchestrator–worker)
09SwarmComplex problems that benefit from debateLangChain (multi-persona)
10ReActDynamic tasks needing tools + adaptationLangChain (manual loop)
11Human-in-the-LoopHigh-stakes / safety / compliance approvalsLangGraph (interrupt)
12Custom LogicMixed-pattern, bespoke branchingLangChain (plain Python)
13RAGGround answers in your own dataLangChain + FAISS
14RAG + CAGStable facts cached + volatile corpus retrievedLangChain + FAISS + prompt caching

Reasoning & agentic techniques

Prompting, reasoning, and retrieval techniques that make an individual agent smarter — complementary to the orchestration patterns above.

#TechniqueWhat it addsStack
15Chain-of-ThoughtReason step by step before answeringLangChain
16Self-ConsistencySample many CoT paths, majority-voteLangChain
17Tree of ThoughtsBranch, score, expand the best (search)LangChain
18ReflexionRetry with accumulated self-feedbackLangGraph
19Plan-and-ExecutePlan up front, then run each stepLangGraph
20ReWOOPlan all tool calls once, then solveLangChain
21Chain-of-VerificationDraft → verify → revise (anti-hallucination)LangChain
22Agentic RAGRetrieve on demand as a toolLangGraph + FAISS
23Corrective RAGGrade retrieval, fall back if weakLangChain + FAISS
24Self-RAGModel gates its own retrieval + groundingLangChain + FAISS
25Memory AgentRecall earlier turns (checkpointer)LangGraph
All 25 are syntax-verified in CI (py_compile on Python 3.11–3.13). Each folder has a README, a runnable main.py, requirements.txt, and .env.example. Browse them: experiments/ on GitHub.

8 · Full-stack example: a support agent

Everything in this tutorial, wired into one runnable app: a customer-support agent that answers questions grounded in a knowledge base and escalates to a human when it can't help. It combines all six pieces:

LangGraph

The agent ⇄ tools loop + memory across turns.

OpenAI

gpt-4o reasoning + text-embedding-3-small embeddings.

Chroma

Persistent vector database for the knowledge base.

RAG

search_kb retrieves grounding context on demand.

LangSmith

Traces every model + tool + retrieval step.

user→ agent · gpt-4o⇄ tools · search_kb / escalate→ grounded reply

Retrieval is a tool the agent chooses to call (agentic RAG), and a sensitive request routes to escalate_to_human instead of a guess.

agent.py (trimmed)
@tool
def search_kb(query: str) -> str:
    """Search the support KB — RAG over the Chroma vector store."""
    docs = store.similarity_search(query, k=4)
    return "\n\n".join(d.page_content for d in docs)

model = ChatOpenAI(model="gpt-4o", temperature=0).bind_tools([search_kb, escalate_to_human])

builder = StateGraph(State)
builder.add_node("agent", agent)                      # gpt-4o reasons
builder.add_node("tools", ToolNode(TOOLS))            # search_kb (RAG) + escalate
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)  # call a tool, or answer?
builder.add_edge("tools", "agent")                    # loop back with the result
graph = builder.compile(checkpointer=MemorySaver())   # memory across turns
run it
pip install -r requirements.txt
cp .env.example .env      # add your OPENAI_API_KEY
python ingest.py          # load KB -> embed -> store in Chroma (once)
python agent.py           # grounded answer, then an escalation

"""Shared settings for the support agent (overridable via environment variables)."""
import os

# Where the Chroma vector store persists on disk.
CHROMA_DIR = os.getenv("CHROMA_DIR", "./chroma_db")
COLLECTION = os.getenv("CHROMA_COLLECTION", "support_kb")

# OpenAI models.
CHAT_MODEL = os.getenv("CHAT_MODEL", "gpt-4o")
EMBED_MODEL = os.getenv("EMBED_MODEL", "text-embedding-3-small")

# Source knowledge base (relative to this folder).
KB_PATH = os.getenv("KB_PATH", "data/knowledge_base.md")
"""Ingest step — load the knowledge base, chunk it, embed with OpenAI, and store
the vectors in a persistent Chroma database.

Run this ONCE before the agent (re-run to rebuild the index):

    python ingest.py
"""
from pathlib import Path

from dotenv import load_dotenv
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

from config import CHROMA_DIR, COLLECTION, EMBED_MODEL, KB_PATH

load_dotenv()  # OPENAI_API_KEY from .env


def build_index() -> int:
    text = Path(KB_PATH).read_text(encoding="utf-8")

    # Split into overlapping chunks so retrieval returns focused, self-contained
    # passages while preserving context across boundaries.
    splitter = RecursiveCharacterTextSplitter(chunk_size=600, chunk_overlap=80)
    chunks = splitter.create_documents([text], metadatas=[{"source": KB_PATH}])

    # Embed with OpenAI and persist to Chroma on disk.
    store = Chroma(
        collection_name=COLLECTION,
        embedding_function=OpenAIEmbeddings(model=EMBED_MODEL),
        persist_directory=CHROMA_DIR,
    )
    store.add_documents(chunks)
    return len(chunks)


if __name__ == "__main__":
    n = build_index()
    print(f"Ingested {n} chunks into Chroma collection '{COLLECTION}' at {CHROMA_DIR}")
"""Customer-support agent.

Ties together the whole stack:
  - LangGraph  — the stateful agent loop (agent ⇄ tools) with conversation memory
  - OpenAI     — gpt-4o for reasoning, text-embedding-3-small for retrieval
  - Chroma     — the persistent vector database holding the knowledge base
  - RAG        — the `search_kb` tool retrieves grounding context on demand
  - LangSmith  — automatic tracing when LANGSMITH_TRACING=true

Run `python ingest.py` first to build the vector store, then `python agent.py`.
"""
from typing import Annotated, TypedDict

from dotenv import load_dotenv
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage, SystemMessage
from langgraph.graph import StateGraph, START
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import MemorySaver

from config import CHROMA_DIR, COLLECTION, CHAT_MODEL, EMBED_MODEL

load_dotenv()  # OPENAI_API_KEY, LANGSMITH_TRACING, LANGSMITH_API_KEY

# Connect to the vector store built by ingest.py.
_store = Chroma(
    collection_name=COLLECTION,
    embedding_function=OpenAIEmbeddings(model=EMBED_MODEL),
    persist_directory=CHROMA_DIR,
)


@tool
def search_kb(query: str) -> str:
    """Search the customer-support knowledge base for relevant policy/help text."""
    docs = _store.similarity_search(query, k=4)  # RAG retrieval over Chroma
    return "\n\n".join(d.page_content for d in docs) or "No relevant policy found."


@tool
def escalate_to_human(reason: str) -> str:
    """Escalate to a human agent when the KB can't answer or the issue is sensitive."""
    return f"Escalated to a human specialist. Reason: {reason}"


TOOLS = [search_kb, escalate_to_human]
model = ChatOpenAI(model=CHAT_MODEL, temperature=0).bind_tools(TOOLS)

SYSTEM = SystemMessage(
    "You are Acme's support assistant. Ground every policy answer by calling search_kb first. "
    "If the knowledge base lacks the answer, or the request is sensitive (refunds over $500, "
    "legal, account security), call escalate_to_human instead of guessing. "
    "Cite the policy you relied on and keep replies concise."
)


class State(TypedDict):
    messages: Annotated[list, add_messages]


def agent(state: State) -> State:
    # The model reasons over the conversation and decides: answer, or call a tool.
    return {"messages": [model.invoke([SYSTEM] + state["messages"])]}


builder = StateGraph(State)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(TOOLS))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)  # agent -> tools, or -> END
builder.add_edge("tools", "agent")                        # loop back after a tool runs
# The checkpointer gives the agent short-term memory across turns of a thread.
graph = builder.compile(checkpointer=MemorySaver())


def ask(question: str, thread_id: str = "demo") -> str:
    cfg = {"configurable": {"thread_id": thread_id}}
    out = graph.invoke({"messages": [HumanMessage(question)]}, cfg)
    return out["messages"][-1].content


if __name__ == "__main__":
    # A grounded policy question (agent should call search_kb):
    print("Q1:", ask("How many days do I have to return an item, and who pays return shipping?"))
    print("-" * 60)
    # A sensitive request on the same thread (agent should escalate):
    print("Q2:", ask("I want a $2000 refund for a laptop that arrived damaged."))
