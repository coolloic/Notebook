PyTorch — deep learning that feels like Python

PyTorch is an open-source deep-learning framework (from Meta, now under the PyTorch Foundation) built to make building and training neural networks intuitive and flexible. Its define-by-run dynamic graphs mean models behave like ordinary Python you can debug step by step — which is why it dominates AI research and the LLM ecosystem.

tensors→ build (nn.Module)→ autograd→ train loop
One line. PyTorch makes experimenting with neural networks feel like writing normal Python — dynamic, debuggable, flexible — so you iterate fast, which is exactly what research and rapid prototyping need.

Why  The problem it solves

Early deep-learning frameworks used static graphs: you defined the whole computation up front, then ran it — fast, but rigid and painful to debug (you couldn't just drop in a print or a breakpoint). PyTorch popularized dynamic graphs: the graph is built on the fly as your code runs, so a model is just Python — you inspect tensors, step through with a debugger, and use normal control flow.

🐍 Pythonic & intuitive

Models are regular Python objects; no separate graph-definition language to learn.

🔬 Fast iteration

Dynamic graphs + easy debugging make experimenting and prototyping quick.

🧠 Autograd

Automatic differentiation computes gradients for you — call .backward() and go.

Mechanics  How it works

The core object is a tensor (an n-dimensional array that can live on a GPU). As you operate on tensors that require_grad, PyTorch records a dynamic graph; calling loss.backward() walks it backward to fill in gradients (autograd). You define a model by subclassing nn.Module, then write an explicit training loop — forward, loss, backward, step.

forward pass→ loss→ loss.backward()→ optimizer.step()↺ repeat
train.py — model + explicit loop
# pip install torch
import torch
import torch.nn as nn

model   = nn.Sequential(nn.Linear(784, 64), nn.ReLU(), nn.Linear(64, 10))
loss_fn = nn.CrossEntropyLoss()
opt     = torch.optim.Adam(model.parameters())

for epoch in range(5):
    for x, y in loader:                 # a DataLoader yields batches
        opt.zero_grad()                 # reset gradients
        preds = model(x)                # forward pass (builds the graph)
        loss  = loss_fn(preds, y)
        loss.backward()                 # autograd fills in gradients
        opt.step()                      # update the weights

That explicit loop is PyTorch's signature: more lines than Keras's fit(), but every step is visible and hackable. Higher-level wrappers (PyTorch Lightning, fastai) hide the boilerplate when you want them to, and torch.compile() (PyTorch 2.x) JIT-compiles the model for a big speed-up without giving up the dynamic feel.

Reach  The ecosystem

🤗 Hugging Face

The vast majority of pretrained models & LLMs are PyTorch-first — the modern NLP hub.

⚡ Lightning / fastai

Higher-level training frameworks that remove loop boilerplate.

🚀 torch.compile

PyTorch 2.x JIT compilation for major speed-ups.

📦 TorchServe / ExecuTorch

Serving and on-device/edge deployment — the production story, much improved.

🌐 Distributed

DDP / FSDP for multi-GPU and large-scale training.

🔁 ONNX export

Export models to run in other runtimes (including TF-adjacent tooling).

The trade-offs  Limitations

What to weigh

Deployment Historically PyTorch's production/deployment story lagged TensorFlow's. It has caught up a lot (TorchServe, ExecuTorch, ONNX), but mobile/edge/browser paths are still generally less mature than TF Lite / TensorFlow.js.

Boilerplate The explicit training loop means more code than model.fit() — great for control, but you write (and can bug) the loop yourself unless you adopt Lightning/fastai.

Overhead Dynamic graphs add some runtime overhead versus a fully static compiled graph (largely mitigated by torch.compile).

Mobile/browser On-device and in-browser deployment is improving but younger than TensorFlow's long-established mobile/JS runtimes.

Net: PyTorch trades a bit of turnkey deployment maturity for best-in-class research ergonomics, flexibility and ecosystem momentum.

When to choose PyTorch

If you…PyTorch fit
Do research or fast prototyping✅ The default choice
Work with LLMs / Hugging Face models✅ PyTorch-first ecosystem
Want intuitive, debuggable, flexible code✅ Dynamic graphs shine
Are starting a brand-new project✅ Most new work uses it
Need heavy mobile / browser / edge deployment⚠️ TensorFlow often smoother
Have an established TensorFlow/TPU stack⚠️ Weigh the switch
Rule of thumb. Building or fine-tuning models, doing research, or working with LLMs → PyTorch. Prioritizing broad deployment (mobile, edge, browser, TPU) → TensorFlow.
