Fine-tuning vs RAG vs prompting

When a base model doesn't do quite what you need, you have three levers to adapt it — prompting, RAG, and fine-tuning. They solve different problems, and the classic mistake is fine-tuning when you needed retrieval, or vice-versa. This is the decision guide.

The one-liner. Prompting changes how you ask. RAG changes what the model knows right now (facts). Fine-tuning changes how the model behaves (skill, style, format). Reach for them in that order of effort.

Framing  The three levers

Cheapest · instant

✍️ Prompting

Craft the input — instructions, examples, format. No training, no infra.

Fresh · factual

🔎 RAG

Retrieve relevant data at query time and put it in the prompt. Knowledge without retraining.

Behavior · style

🎚️ Fine-tuning

Train the model's weights on examples to change how it responds.

Key distinction: for knowledge ("what does it know?") use RAG; for behavior ("how does it act / what format / what style?") use fine-tuning. Fine-tuning is a poor way to inject facts — they go stale and it can hallucinate.

Lever 1  Prompting

✍️ Prompting

Great for Steering tone, format and simple behavior; the first thing to try for almost everything. Zero training, instant iteration, works on any model. See prompt & context engineering.

Limits Bounded by the context window; can't add lots of private knowledge permanently; long few-shot prompts cost tokens every call.

Lever 2  RAG (retrieval-augmented generation)

🔎 RAG

Great for Grounding answers in your data and current facts — docs, tickets, a knowledge base — that change often. Update the data, not the model; cite sources; scales to huge corpora. See RAG vs CAG.

Limits Answer quality is capped by retrieval quality; adds infra (embeddings + vector DB) and per-query latency; doesn't change the model's skills or style.

Lever 3  Fine-tuning

🎚️ Fine-tuning

Great for Teaching a durable behavior: a consistent style/voice, a niche format or task, a domain's language, or shrinking a big prompt into the weights (lower per-call cost/latency). Modern LoRA/PEFT tunes a small adapter cheaply rather than the whole model.

Limits Needs a quality labeled dataset (often hundreds–thousands of examples), a training pipeline, and eval; facts baked in go stale and can't be updated without retraining; risk of overfitting or degrading general ability. Highest effort of the three.

Common myth: "fine-tune it on our docs so it knows them." That's usually the wrong tool — use RAG for knowledge. Fine-tune for how it responds, not what it knows.

Not either/or  Combining them

These stack, and mature systems use all three: a fine-tuned model for the right behaviour/format, fed retrieved facts (RAG) for grounding, driven by a well-engineered prompt.

🎚️ fine-tuned behaviour + 🔎 retrieved facts + ✍️ good prompt
Order of adoption. Exhaust prompting first (cheapest), add RAG when you need private/fresh knowledge, and only fine-tune once you've proven prompting+RAG can't get the behaviour you need — and you have the data and evals to do it well.
